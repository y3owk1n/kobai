# `.gitignore` is the one statement of what a checkout generates

Every other ignore file in this repository has to agree with it **at every depth**. Two do
not have to be told twice and one does:

- **`biome.json` delegates.** `vcs.useIgnoreFile` makes a gitignored path out of the lint
  gate's scope outright, so `files.includes` keeps only what an ignore file can never
  carry — the generated artifacts this repository **tracks**.
- **`.dockerignore` cannot delegate**, because Docker offers nothing equivalent. So there the
  answer is the glob, and the rule is enforced instead: a pattern naming something
  `.gitignore` ignores has to match at the same depths.

`tests/the-gate-lints-what-git-tracks.test.ts` and
`tests/nothing-git-ignores-reaches-the-build-context.test.ts` keep the two halves true.

[ADR-0039](./0039-the-lint-gate-fails-on-every-finding.md) decided what "green" means for a
file the gate looks at. This decides which files those are — the other half of the same
guarantee, and the half that had never been decided at all. #203 is where it was found, in
`biome.json`; the identical mistake in `.dockerignore` is a section below, and it had been
sitting there the whole time.

## What went wrong in `biome.json`

The exclusion list carried `"!.devbox"`, which is **root-anchored**: it excluded the
workspace's own `.devbox` and nothing else. `reference/` ships a `devbox.json` of its own
with eleven scripts — it is the Project a maintainer boots, and
[ADR-0029](./0029-the-reference-project-is-the-release-gate-and-content-is-built-first.md)
makes it the release gate — so `cd reference && devbox run build` leaves a nix profile
manifest behind. Biome then scanned it and the gate went red (#203):

```
format ━━━━━━━━━━━━━━━━━━━━━━━━━━━
  ✖ File content differs from formatting output
    1 │ - {"elements":{"nodejs":{"active":true,"priority":6,"storePaths":["/nix/store/ns9a…
```

Three things made it expensive out of proportion to the one-character fix:

- **Nothing in the failure names `reference/`.** It names a nix store path and a
  `manifest.json`, in a directory `.gitignore` carries and `git status` therefore cannot
  show, produced by a command with nothing to do with formatting. The only tell is the file
  count — `Checked 299 files` becomes `Checked 643 files` — and nobody reads it.
- **`devbox run format` does not repair it.** It rewrites the manifest, which is generated;
  the next `devbox run` inside `reference/` puts it back in its original form.
- **It was not the only instance.** `.scratch/` is gitignored, AGENTS.md hands it to
  agents as scratch space, and `includes` never mentioned it — so the gate linted whatever
  was left there, and had done since the directory was invented. That one had no ticket
  because whoever hit it deleted the file and moved on.

## Why not `"!**/.devbox"`

Because it answers the instance and leaves the class. The list would then have said
`node_modules`, `dist` and `.devbox` are not source — three facts `.gitignore` already
states, in a second place, in a dialect with different anchoring rules. That second copy is
the whole failure: it was the narrower of the two answers, and nothing could see which one
was being used.

The same scoping mistake is already recorded one section down in ADR-0039, where a bare
`devbox.json` pattern in `overrides` reached the workspace's manifest and not the reference
Project's. Fixing a glob is what was done then. Fixing the arrangement that keeps producing
the glob is what is done here.

## The rule, and where each half lives

**`.gitignore` says what is not in the repository. `includes` says which of the files that
are in it are generated.** No path belongs in both, and the test fails naming any exclusion
git tracks no file under.

That leaves five entries, and every one of them is a **tracked** artifact some other test
regenerates and byte-compares — which is precisely why Biome must not reformat them:

| Excluded | Regenerated by | Held by |
| --- | --- | --- |
| `**/migrations/meta` | `devbox run db:generate` | drizzle-kit's own snapshots |
| `packages/core/openapi.json` | `devbox run openapi:generate` | `packages/core/src/http/openapi.test.ts` |
| `packages/client/src/schema.ts` | `devbox run openapi:generate` | `packages/client/src/schema.test.ts` |
| `packages/create-kobai/template` | `devbox run template:generate` | `tests/create-kobai-matches-the-reference-project.test.ts` |
| `**/pnpm-lock.yaml` | pnpm | the lockfile itself |

The other four name one specific path each, at the one place it can exist.
`**/pnpm-lock.yaml` was `!pnpm-lock.yaml`, and is the one entry that is **inert today**:
Biome 2.5.8 processes no YAML at all, so the exclusion reports nothing whether it is there or
not. It is kept because a lockfile is a tracked generated artifact and so belongs here under
the rule above, and depth-anchored so that the day Biome ships a YAML formatter it is already
right rather than red — in a second file, which is exactly how #203 arrived in the first
one. Nothing in the test below stands on it, and the note there says so: an assertion that
would pass with the thing it checks deleted is decoration.

## What this rests on, and what it costs

- **Biome reads the ignore file itself; no `.git` is required.** Verified directly against a
  directory holding a `biome.json` and a `.gitignore` and no repository at all.
- **It does fail outright when `useIgnoreFile` is on and there is no ignore file beside
  the config** — `Biome couldn't find an ignore file in the following folder`, as a
  configuration error rather than a lint finding. `.gitignore` is tracked at the repository
  root, so that state is not reachable here; it is written down because the failure names
  neither this decision nor the file it wants.
- **A path added to `.gitignore` leaves the gate's scope silently.** That is the mechanism
  working — a file git does not track is not this repository's source — but it is a real
  consequence, and the place to notice it is the `.gitignore` change, not this one.
- **Nested ignore files are honoured**, which is what makes the rule true at depth rather
  than only at the root. Verified the same way: a `.gitignore` in a subdirectory takes its
  own subtree out of the scan.

A generated Project is unaffected in both directions: it ships no `biome.json` at all, so
there is no second copy of this list to keep in step and nothing in
`packages/create-kobai/src/adaptations.ts` to add.

## An agent worktree is the case that proves the rule is worth having

`.claude/worktrees/` is where a harness that runs work on a branch puts a **whole second
checkout** — `biome.json` and all. It was neither tracked nor ignored, so
`devbox run lint` in a checkout that had one did not merely lint three copies of the
repository: it **failed outright**, at `Found a nested root configuration, but there's
already a root configuration`, naming a directory the reader is not in. That is the same
diagnostic ADR-0039 records as the reason `biome.json` cannot carry a comment, and the same
complaint #203 makes about a failure that points nowhere useful.

The fix is one line in `.gitignore` and nothing else, which is the rule above doing its job:
git does not track it, so it can never belong in `files.includes`. `.claude/skills` stays
tracked, because git does not ignore a file it already has.

Two things about it are worth keeping:

- **It is the first entry in either ignore file to hold an interior slash**, so it is
  anchored to the repository root rather than matching at any depth — and the
  `.dockerignore` rule below had to learn the difference, or it would have demanded a `**/`
  that would be wrong.
- **`.dockerignore` gets `.claude` too**, plainly and not under the derived rule, because
  the directory only exists at the context root. Without it `COPY . .` sends every agent
  worktree in the checkout into the build context.

## The same mistake is in `.dockerignore`, and there is no `useIgnoreFile` there

`.gitignore` matches a slashless pattern at any depth. A `.dockerignore` pattern is anchored
at the **build context's root** unless it opens with `**/`. So the two files say the same
words and mean different things — and both `.dockerignore`s carried `.devbox`, `.env` and
`.env.*` root-anchored, directly beside `**/node_modules` and `**/dist`, which somebody had
already got right.

The workspace `Dockerfile` opens with `COPY . .` and its runtime stage is
`COPY --from=build /repo /repo`; the prunes in between remove `tests`, `packages/client`,
`packages/create-kobai` and the Admin's source, and touch none of this. Measured against a
real `docker build` rather than reasoned about — with the old patterns
`reference/.devbox/nix/manifest.json` and `reference/.env` both arrive in the context, and
with `**/` in front of them neither does while an ordinary file beside them still arrives.

**`.env` is what makes this more than housekeeping.** `.gitignore` hides it at every depth,
so `git status` would never show you one sitting in `reference/`, and a credential that
reaches a layer is in that layer forever — the reason `.npmrc` is mounted as a build secret
rather than copied at all
(AGENTS.md § Writing tests, under the image seam).

Docker offers nothing like `vcs.useIgnoreFile`, so here the answer **is** the glob — which is
why the rule is enforced rather than delegated. `tests/nothing-git-ignores-reaches-the-build-context.test.ts`
derives it: a `.dockerignore` pattern naming something the governing `.gitignore` also
ignores has to match at the same depths. It judges `.git`, `docs`, `*.md` and `.npmrc` not at
all, because no ignore file names them — those are tracked or absent, and how they are
anchored is a build-context question rather than this one. It checks **three** files, the
template's included: that copy is generated, so a fix here reaches a Developer only through
`devbox run template:generate`.

## Consequences

- **`devbox run build` inside `reference/` no longer reddens the gate**, and neither does
  anything else left in a gitignored directory at any depth.
- **`.scratch/` stops being linted**, so a prototype an agent leaves there is no longer a
  finding — which is what AGENTS.md always said that directory was for.
- **The next artifact directory needs one edit, not two.** Adding it to `.gitignore` is the
  whole change; a matching entry in `biome.json` now fails the build rather than passing
  unnoticed.
- **Nothing a checkout generates below the root reaches a build context either**, and
  `reference/.env` in particular no longer does.
- **`dist` is excluded by `.gitignore` alone**, and
  `tests/the-gate-lints-what-git-tracks.test.ts` lints a fixture holding a file under it, so
  that deletion is checked rather than assumed. **`node_modules` needed no replacement at
  all**: Biome ignores it unconditionally — measured with the `vcs` block deleted *and* no
  ignore file present, where `dist` and `.scratch` are both scanned and `node_modules` is
  not — so `!**/node_modules` had been inert for as long as it had been written down.
